# AetherGo 路线图

> v0.1 的定位:**规则正确、能下、代码简单**。规则正确性由单测
> (提子 / 自杀 / 劫 / 数子)+ 随机对局模糊测试(make/unmake 往返不变量,
> 合法列表逐步复原)保证;搜索是第一版 UCT + 纯随机演棋,刻意没有堆技巧。
> 下面按「先补齐规则缺口 → 再提升演棋质量 → 再升级搜索 → 最后上工程化」排优先级,
> 每一期都写清楚**验收方法**,不做完不算完。

现状基线(本机 Node 24,桌面级 CPU):约 **4.5k 演棋/s**,
高级档 9k 演棋 ≈ 1.9s,引擎 chunk gzip 约 5 KB(**预算 35 KB**,与象棋引擎同档)。

本路线图**只覆盖引擎本身**:WebOS 应用侧(死子标注界面、棋谱导出、棋钟等)不在此列。

## P0 —— 规则与终局完整性(不做完,棋就不完整)

1. **禁全同(position superko)**
   现在只有 simple ko(单劫禁一手)。循环劫、三劫等会在「同一局里反复来回提」。
   - 做法:对局历史维护 Zobrist 键集合(主线程与搜索树各自维护到根的链),
     落子后键已存在即非法。注意与「打劫」提示的兼容:simple ko 是 superko 的特例。
   - 验收:构造三劫循环局面,引擎不再无限来回;模糊测试里加入「盘面重复」检测归零。
2. **终局死子处理**
   数子法假设「盘上皆活」—— 双停时残留的死子会把结果算错(引擎对局里死子
   通常已被提掉,但玩家认输前的双停不是这样)。
   - 做法:引擎侧提供「死子估计」API(对每个孤块做强气/眼位判定,
     或直接用 MCTS 对「对方先手提这块」做小预算评估),UI 侧据此标注、
     用户可手改后重算。
   - 验收:构造「双停时白角残留一块死棋」的局面,估计结果与实战提子后数子一致。

## P1 —— 演棋策略升级(同样的演棋数下,棋力涨一大截)

按「收益 / 复杂度」排序,逐项**单独开关、单独对拍**:

1. **局部响应**:演棋时以高概率在上一手附近(2 格内)选点 —— 围棋着法
   高度局部化,这一条通常是最划算的改进。
2. **战术响应**:上一手把我叫吃 → 优先逃/反提;上一手送吃 → 优先提。
   用现成的 groupInfo(气数)就能做,不用模式库。
3. **模式/形状先验**:3×3 局部模式表(手工几十条,如「尖」「虎」「爬二路」),
   给候选点加权而非硬性排除。
4. **RAVE(快速行动值)**:同色统计回传,早期树收敛快数倍;注意与 UCB
   的混合系数要随访问次数衰减。

**验收口径**(沿用 webos 的规矩,确定性优先):
- 固定演棋数下,新版本 vs 当前版本**成对自对弈**至少 200 局(先后手各半),
  胜率显著才算通过;
- 「9k 演棋 vs 旧版 24k 演棋」能打平,即视为效率提升 2.5 倍;
- 引擎测试全绿不许回归(规则与撤销不变量与棋力无关)。

## P2 —— 搜索增强

1. **树复用**:下一手搜索继承上一手的子树(只保留根着法分支),
   等效预算翻倍;webOS 侧一局连续行棋是常态,收益直接。
2. **首着先验 / progressive widening**:根节点按启发分给先验,
   避免低预算下访问次数摊平。
3. **胜率 → 目差**:演棋时同时统计平均目差,信息行可以显示
   「胜率 62% · 黑约 +3 目」,终局前对「停还是填」更有指导。

## P3 —— 工程化

1. **体积闸门**:引擎 worker chunk 的 **gzip ≤ 35 KB**,与两个象棋引擎同一档预算。
   闸门挂在 webos 侧 `tools/check-size.mjs`(靠 worker 里的字符串标记
   `go-engine-v1` 定位 chunk),`npm run build` 会拦。

## 明确不做(已拍板,不是「还没做」)

- **不做神经网络**:纯 JS + 纯 MCTS,不接 ONNX/WASM 推理、不内置权重文件 ——
  保持与黑白棋、两个象棋引擎一致的「零依赖单文件」风格。
- **不做 GTP / SGF 引擎侧支持**:不接主流围棋 GUI;SGF 导出属于 WebOS 应用侧。
- **不做开局库**:不内置任何着法表,开局一律进搜索。
- **不做多线程**(根分裂 / Lazy SMP 之类):单线程到底。
- **暂不上 WASM**:当前未启动。等 JS 侧优化到头(演棋策略与树复用做完)再评估。
- 不接第三方引擎对打:棋力只靠自对弈 A/B 定方向,拿 A/B 胜率换算 Elo 没有意义。
- 不为了「看起来强」去堆不验证的技巧:每一项都要有对拍或自对弈数据。
